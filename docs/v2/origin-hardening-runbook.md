# Runbook: закрытие origin (один раз на VPS)

Контекст: находка S5-14 аудита 2026-10-07. Все сайты портфеля сидят на одном IP VPS. Если origin виден
напрямую, по IP можно связать весь портфель (footprint) и обойти Cloudflare.

Провижн (`services/provisioning.py`) проверяет только факт: `origin_exposure_warning(ip)` шлёт
`GET http://<ip>/` с неизвестным Host. Ответ 2xx (заглушка aaPanel «Site is created successfully!»)
попадает в `warnings` результата и во флеш панели. Само закрытие делается руками один раз, не на каждый
сайт:

1. **Default-vhost на 80 и 443 с `return 444`** (nginx закрывает соединение без ответа). На 443 нужен
   нейтральный сертификат — не `*.aapanel.com`. Так неизвестный Host/SNI ничего не раскрывает.
2. **Файрвол VPS: 80/443 только с диапазонов Cloudflare** (https://www.cloudflare.com/ips/) **И с публичного
   IP бокса.** Без второго пункта провижн ломается насовсем: `probe_marker` ходит с бокса прямо на IP origin
   (минуя Cloudflare), все пробы падают, сайт навечно остаётся в `provisioning` на шаге `verify`, а свип
   бьёт по нему каждую итерацию. Что сделать:
   - узнать публичный IP бокса за NAT (на боксе, PowerShell): `(Invoke-RestMethod https://api.ipify.org)`;
   - добавить его в белый список 80/443 на VPS вместе с диапазонами Cloudflare (если провайдер выдаёт
     динамический IP — обновлять запись при смене, иначе провижн снова встанет);
   - проверить С БОКСА (PowerShell, `curl.exe`, не алиас `curl`):
     `curl.exe -s -o NUL -w "%{http_code}" -H "Host: <уже провиженный домен портфеля>" http://<ip>/` — ответ должен
     прийти (200/301/404, но не `000`; на неизвестный Host при default-vhost 444 `000` как раз норма);
     а с любого стороннего хоста тот же запрос должен давать `000` или таймаут.
   Провижн теперь доказывает origin маркер-файлом `cm-probe-<hash>.txt` в docroot сайта (имя уникально
   на домен): нужен 200 с его содержимым. Файл безвреден, его можно удалять — следующий провижн перезапишет.
3. **Порт панели 18839 закрыть файрволом** после SSH-туннеля (S5-03): панель не должна быть на открытом
   порту.

Проверка после правок (команда запускается на VPS под Linux, оболочка bash):
`curl -s -o /dev/null -w '%{http_code}' -H 'Host: x.invalid' http://<ip>/` должен давать `000` (пустой ответ),
а следующий provision — без `warnings`. С бокса (Windows/PowerShell) тот же запрос, но другим синтаксисом:
`curl.exe -s -o NUL -w "%{http_code}" -H "Host: x.invalid" http://<ip>/` — если бокс в белом списке (п. 2),
444 даст `000` и здесь.
