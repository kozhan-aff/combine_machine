# Живые форматы для досье конкурентов — пробы 2026-10-10

Пробы на боксе `192.168.1.77` (план А, Задача 1). Формат внешних ответов не угадываем: ниже то, что
вернули живые сервисы. Образцы лежат в `backend/tests/fixtures/research/`. Код приложения не менялся.

Как выполнялось: python-скрипты через stdin в контейнере `backend` (`docker compose exec -T backend python -`),
а не curl в cmd (избегаем экранирования JSON). Эквивалент запросов из плана — те же эндпоинты и тела.

## 1. A-Parser: SERP и страницы конкурентов

Команда: `AParserClient().serp_urls("Durev VPN обзор", limit=10)`, затем `fetch_html(url)` по каждому URL,
пока не набрано два HTML длиннее 5000 символов.

**Форма SERP** (`aparser_serp_durev.json`): `{"query": "...", "urls": [10 строк]}`.

**ВСЕ 10 URL — редиректы `https://www.google.com/goto?url=<base64-подобный токен>`**, прямых URL нет.
Токен непрозрачный (`CAES...`, начинается одинаково `CAES` + `Hr`/`B6zsw`), домен из него без запроса не
достать. Значит, для досье нельзя фильтровать выдачу по домену/блэклисту до скачивания: сначала
`fetch_html`, потом домен — из финального URL (либо `<link rel=canonical>`/`og:url` в HTML). Токены
живут недолго — это ещё одна причина не хранить SERP как ссылки на будущее.

**`fetch_html` по `goto`-URL отдаёт HTML целевой страницы** (редирект проходит внутри A-Parser, ответ
200 с реальным телом): из 3 попыток — 2 успеха (140 246 и 130 145 символов), 1 отказ:
`fetch_html ...: не-200 ('596 HTTPS(C) proxy error: Error: 502 Bad Gateway')` (клиент вернул `None`/пустое;
в логе — исключение-предупреждение, не падение). Т.е. часть goto-ссылок будет недоступна из-за прокси — код
досье обязан пропускать такие URL и брать следующие, как и делает цикл пробы.

Что оказалось за goto (запрос «Durev VPN обзор» нашёл не обзорные статьи, а сайт самого бренда):
- `competitor_1.html` — 140 246 симв., `<title>Durev VPN | Новости – Telegram</title>`, публичная лента канала
  `t.me/s/durevvpn` (`<link rel="canonical" href="/s/durevvpn?before=149">`). Не статья-конкурент, но
  реальный сложный HTML: 1 инлайновый `<style>`, внешние стили `//telegram.org/css/*.css`
  (протокол-относительные URL).
- `competitor_2.html` — 130 145 симв., `<title>Кабинет - Durev VPN</title>`, Next.js-приложение (кабинет
  сервиса): внешние стили `/_next/static/css/*.css` (относительные корневые), 0 инлайновых `<style>`,
  локализация зашита JSON-строками в скрипте. Слова password/ключ в файле — только строки интерфейса, не секреты.
- Оба файла сохранены целиком (< 400 КБ, обрезки нет). Тестам на извлечение (Задачи 5–6) это даёт два
  разных вида разметки: серверный HTML (Telegram) и JS-приложение (Next.js).

**CSS** (`competitor_1.css`): первый `<link rel="stylesheet">` в `competitor_1.html` —
`//telegram.org/css/font-roboto.css?1` (6166 симв., скачан тем же `fetch_html` по `https://telegram.org/css/font-roboto.css?1`,
вернул `str`). Содержимое — только блоки `@font-face` Roboto (`src: url('../fonts/Roboto/...woff2')`,
`unicode-range`), цветов и раскладки там нет. Для проверки извлечения палитры/шрифтов подходит как
фикстура шрифтов, но не палитры; палитру брать из `telegram-web.css` либо инлайнового `<style>`. Пустым не является.
Урок для кода: ссылки на стили бывают протокол-относительными (`//host/...`) и корневыми (`/_next/...`) —
разрешать относительно финального URL страницы (`urljoin`).

## 2. Browserless (`/screenshot`, `/function`)

Адрес. С бокса Browserless на `http://127.0.0.1:3000`, но **из контейнера `backend` `127.0.0.1:3000` —
`Connection refused`**; рабочий адрес из контейнера — `http://192.168.1.77:3000` (корень `/` отдаёт 404, сервис
жив). Токена нет. Клиент приложения должен ходить по `192.168.1.77:3000` (настройка в конфиге, не localhost).

**`POST /screenshot`** тело `{"url":"https://tunnelnotes.xyz/","options":{"fullPage":true,"type":"png"},"viewport":{"width":1366,"height":768}}`:
HTTP 200, `Content-Type: image/png`, 646 511 байт, магия PNG (`\x89PNG`), ~1.5 с. Размер картинки 1366×4138.
Фикстура `browserless_screenshot.json`: `{"status":200,"content_type":"image/png","bytes":646511}`.
Тот же запрос с `"fullPage": false`: 200, PNG 1366×768, 142 623 байта.

**`POST /function`**, `Content-Type: application/javascript`, тело — ES-модуль с `export default async function ({ page })`:
HTTP 200, `Content-Type: application/json; charset=UTF-8`. Тело ответа (фикстура `browserless_function.json`, дословно):

```json
{
  "data": {
    "scrollWidth": 900,
    "innerWidth": 390
  },
  "type": "application/json"
}
```

Т.е. ответ — **весь возвращённый из функции объект `{data, type}` как есть** (конверт НЕ снимается, а
не только `data`). Читать значения надо из `resp["data"]`. Формат `Content-Type: application/json` с
`{"code": ...}` не понадобился (первый вариант дал 200). Проверка мобильного переполнения работает:
`scrollWidth=900` > `innerWidth=390` → горизонтальный скролл на 390 px обнаружен.

## 3. Читает ли Claude Code через шлюз PNG из `/workspace`

Шлюз `http://192.168.1.77:3033/v1/chat/completions`, модель `sonnet`, без ключа (запросы слали из контейнера
backend — шлюз доступен по LAN-адресу). PNG положен на хост в `D:\claude-code\workspace\` (через
`docker compose cp backend:/tmp/probe.png ...`), там же он виден шлюзу как `/workspace/...`.

1. `/workspace/probe.png` — **полностраничный** снимок 1366×4138 (646 КБ): ответ шлюза 200, модель сообщила, что
   инструмент `Read` доступен, но файл «слишком большой, превышает лимит 2000x2000px» и содержимое не показано.
   `READ_DENIED` не вернулся, но и описания нет.
2. `/workspace/probe2.png` — снимок только окна 1366×768 (143 КБ): **прочитан и описан верно** (~6.6 с):
   «скриншот страницы tunnelnotes.xyz с обзором сервиса «TestVPN» (партнёрская статья с баннером и блоками
   «Приватность», «Скорость», «Доступ по всему миру»)».

**Вердикт для §7.2 спеки (план В): да, Read PNG через шлюз работает — НО только для изображений в пределах
2000×2000 px.** Полностраничный скриншот длинной страницы (высота > 2000 px) не читается. Для критика
нужно снимать по частям: viewport-снимки (`fullPage:false`) либо нарезка длинной страницы на куски высотой
≤ ~1800 px (например, `options.clip`, либо несколько скриншотов со скроллом), а не один fullPage-PNG.

## Живой прогон досье на боксе (2026-10-10, сайт #1 tunnelnotes.xyz, оффер Durev VPN ru/RU)

- Результат: `done_warn`, 4 источника за ~4.5 мин: `howto` — 2 goto-страницы без canonical (`goto1`/`goto2`, 337 и 579 слов),
  `market` («лучший VPN Россия») — proprivacy.com (6859 слов, 20 заголовков, таблица, 11 FAQ, 60 чисел) и ru.wizcase.com
  (4125 слов, 4 таблицы). `review` и `comparison` — ни одной живой страницы.
- Почему пусто по бренду: SERP «Durev VPN обзор» = YouTube (canonical `undefined`, отсев), сайт бренда (`og:url
  https://durevpn.com`, `og:site_name Durev VPN` — отсев фильтром бренда, как задумано) и 4 из 6 goto-ссылок упали в
  A-Parser с `596 HTTPS(C) proxy error … 502 Bad Gateway`. То есть у малого бренда обзоров в выдаче нет — писатель (план Б)
  берёт факты из `market`-досье и датасета, а не из «обзоров».
- **Net::HTTP НЕ отдаёт конечный URL** после `google.com/goto` (спека §4.2 — вопрос закрыт): `fetch_html` режет шапку, редирект
  следует внутри A-Parser. Домен судится только по `canonical`/`og:url`/`og:site_name`; без них — `goto{rank}`.
- Скриншоты не снимались (`RESEARCH_SCREENSHOTS=false` по умолчанию) — включить на `/settings/keys` при живой проверке плана В.
- Что улучшить (план Б): повтор `fetch_html` один раз при 502 прокси (половина выдачи теряется), кириллические имена площадок
  в фильтре, пауза перед повторной сборкой пустого досье в свипе.


## Живой прогон плана Б на боксе (2026-10-11, сайт #1 tunnelnotes.xyz, оффер Durev VPN ru/RU)

Шлюз модели — `http://192.168.1.77:3033` (headless Claude CLI): писатель `sonnet`, критик `opus`.

**Что измерено и подтверждено**
- Ответ критика — ЧИСТЫЙ JSON без ограды и прозы (sonnet 10,7 с, opus 12,5 с на короткой странице; 74–85 с на
  странице 800 слов с 16 тыс. знаков правил). Риск «ответ не по форме» на практике низкий.
- Длинный вход почти бесплатен (31 тыс. знаков + ответ в одно слово — 3 с). Длинный ВЫХОД медленный: свободный текст
  ~160 знаков/с, а JSON при большом задании ~50 знаков/с. Выжимка сводного файла правил (31 тыс. → 16 тыс. знаков) — 378 с;
  две попытки с таймаутом 600 с не уложились. Таймауты подняты: выжимка 1500 с, писатель 1200 с, критик 600 с.
- Страница писателя (700–1150 слов JSON по схеме `PageDoc`) — 3–5 мин; три страницы сайта — 10–14 мин. Схема проходит с
  первого раза (ни одного повтора за два прогона).
- Правка страницы по замечаниям (круг) — 3–5 мин + вычитка ~1,5 мин.

**Что вскрыл прогон (и что поправлено в ту же ночь)**
- Воркер не видел папку правил: bind-том «протух» после того, как git пересоздал каталог `content_guides/` (плоская папка).
  Лечится пересозданием контейнера: `docker compose up -d --force-recreate worker`. Код теперь считает невидимую папку
  стоп-условием авто-одобрения («папка правил письма не видна этому процессу»).
- Страницы сайта несли `offer_id` старого оффера (TestVPN) при сайте, привязанном к Durev VPN: «Переписать» теперь берёт
  оффер САЙТА и переписывает `Page.offer_id`.
- Оператор заменил 17 файлов правил одним сводным (`iGaming-TEXT-v5.0-kratko.md`, 31 273 симв.). Потолок выжимки на файл
  теперь растёт, когда файлов мало (1 файл → 16 000). Модель сперва вернула роль `skip` («другая ниша») — промпт уточнён:
  предметно-нейтральные правила (стиль, структура, данные, антипаттерны) переносятся на нишу сайта. Итог: роль «обоим»,
  15 944 симв., разделы «Приоритеты / Интент / Данные и источники / Целостность данных / Структура / Типы страниц / EAV / Стиль».
- Первый черновик обзора содержал ложную исключительность («оплата только криптовалютой», «личного кабинета нет»), выведенную
  из формулировки фактов. Факты бренда переписаны без «только»; в правила писателя добавлено «не достраивай за источник»
  и «не вычисляй производные числа» (писатель считал цену за устройство и за гигабайт — критик их не находил в источниках).
- Оценка «N/10» в вердикте страницы: схема обязывала писателя её ставить, а правила оператора запрещают число без
  методики → оценка стала необязательной (`score: null`).
- Объём: ориентир 1500–2200 слов недостижим без воды для бренда с десятком фактов (обзор — 600–900 слов), а правила
  оператора прямо запрещают добивать объём. Критик теперь бракует только явный недобор/перебор (жёсткие границы), ориентир
  остаётся в брифе.
- Вердикт критика разделён на `issues` (с чем публиковать нельзя) и `advice` (пожелания, на решение не влияют): строгий
  редактор с правилами оператора давал 17 замечаний вперемешку.
- Круг переписывания был письмом ЗАНОВО (писатель не видел прежний текст) — не сходился: старые замечания уходили, новые
  домыслы приходили. Теперь круг — правка прежнего JSON по замечаниям.

**Итог по воротам авто-одобрения на живых данных**
- Критик НЕ одобрил ни одной страницы за два круга: на каждую вычитку находит 7–11 блокирующих замечаний, после правки —
  новые (в основном обязательные по правилам оператора стиль и ИИ-маркеры: точка с запятой, стоп-фразы, частота тире,
  однотипные зачины; реже — остаточные домыслы). Страницы остались черновиками с подробными замечаниями; на сайт ничего
  не ушло. Это штатное поведение ворот: при строгих правилах оператора «ноль замечаний» за два круга — редкость.
- Что решать оператору (не код): (а) оставить так — критик готовит и размечает, одобряет человек одним кликом;
  (б) считать стилистические замечания пожеланиями (тогда блокируют только факты/право/бренд/язык/копирование);
  (в) дать больше кругов правки (сейчас 2; круг ≈ 5–6 мин на страницу).
